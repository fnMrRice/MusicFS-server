# Server 插件化细化设计

状态：2026-10-11，基于当前实现的扩展设计；本文不代表新增插件、C++ SDK 或新协议已交付。当前代码与证据见[插件协议 1.0](contracts/plugins/v1/README.md)、[插件管理验收](validation/plugin-management.md)及[实施记录](validation/progress.md)。共同约束见[跨端插件边界](../../docs/plugin-boundaries.md)，原生构建规则见[CMake / C++23](../../docs/native-plugins.md)。

## 1. 架构能力与前置缺口

现有架构支持继续插件化：Server 保持 Go 模块化单体，来源适配、内容提取和音频处理在受管 Worker 中执行；控制面与数据面已经分离。新工作优先扩展现有角色和受控资源服务，不要求重写已交付的 Go 插件。需要 C++ 库或原生性能的插件使用 CMake / C++23，交付独立 Worker 可执行程序。

Server 的进程模型与 Client 的单进程 DLL 模型分别维护。两端可复用算法源码、格式模型和测试向量，各自构建宿主适配层，不承诺同一二进制或同一 SDK 可直接运行于两端。

| 项目 | 当前事实 | 扩展前必须处理 |
| --- | --- | --- |
| 角色 | `provider`、`scraper`、`audio`；其他角色被拒绝 | 新角色先增加协议、注册、授权、调度和生命周期适配 |
| 插件接入 | 官方插件按固定身份和已知配置接入；统一程序通过参数选择内置角色 | 新插件 ID 需要 Host 注册/适配，不能只放入 manifest 或更换程序路径 |
| 控制协议 | JSON-RPC 2.0 / stdio，协议版本精确为 `1.0` | 不是“任意 JSON-RPC 实现都兼容”；须符合角色专用握手、DTO、版本和能力检查 |
| 数据通道 | 音频、NCM、本地 Scraper 已有任务限定 loopback 二进制通道 | 各通道契约不同；未交付通用节点 PCM 总线或共享内存 SDK |
| 来源资源 | Local Files 为本地根、路径与稳定读取；在线主要为资料/账号 | 原生 NAS、在线整曲先扩展资源模型和受控读取，见[NAS / Bilibili 计划](implementation/nas-bilibili.md) |
| 动态管理 | 插件/实例开关、动态启用、配置重建、工作租约与 SSE 已实现；停用保存后重启生效 | 安装、下载、通用第三方发现、升级回滚及管理 CLI 另行交付 |
| 安全隔离 | Broker 校验 Host 提供的权限；仅管理员配置的受信任程序 | 独立进程不等于 OS 沙箱；第三方不可信插件必须先验证额外隔离 |
| 原生实现 | 当前官方插件为 Go；尚无 C++ Worker 一致性验收 | C++23 工具链、协议绑定、实际数据通道及平台制品需验证 |

具体固定身份校验位于 `src/pluginhost/process.go`、`online_process.go`、`src/pluginproto/online.go`、`src/plugins/audioffmpeg/processor.go`、`src/plugins/scraperlocal/host.go`。因此当前可论证的是**插件化架构可扩展**，不能据此宣称**通用第三方 SDK 已可用**。

## 2. 按职责拆分的插件矩阵

表中“已有”只指该行所述范围；“待扩展”是设计任务，不能直接写进当前 manifest/config。是否使用 C++ 根据实际依赖和性能验证选择，选择后统一使用 CMake / C++23。

| 扩展职责 | 归属与可复用部分 | 插件可以输出 | Host 保留的决策 | 当前状态 / 缺口 |
| --- | --- | --- | --- | --- |
| 本地文件、挂载 NAS | Music Provider / Local Files | 文件观测、基础标签、可得格式、受限资源请求 | 根授权、稳定来源身份、扫描发布、资产版本 | 已有；实际 NAS 环境另验收 |
| 原生 SMB / NFS | 两个独立 Music Provider | 远端枚举、版本证据、受控读取 | 目标白名单、来源身份、完整扫描判断、租约 | 待扩展远端资源；依赖若需 C++ 则独立 C++ Worker |
| 在线平台、Bilibili | 各平台独立 Music Provider | 搜索、资料、平台歌单/推荐、授权后的来源描述 | 账号归属、凭据服务、导入/同步发布、播放权限 | 三个平台资料/账号已有部分实现；B 站与整曲资源待扩展 |
| 歌词、封面、专辑资料 | 独立 Scraper；平台适配也独立注册 | 候选、来源依据、语言、适用范围和内容引用 | 下载/格式校验、人工锁、选用、Media Store 发布 | 本地歌词/封面已有；在线抓取、专辑资料与查询修正需相应 DTO/权限增量 |
| 解密、解复用、解码、编码、封装 | Audio Processor；算法可在 Worker 内组合 | 受控音频输出、真实格式、延迟和定位信息 | 资产授权、处理计划、表示版本、播放会话及缓存发布 | FFmpeg 与 NCM 已有；通用逐节点协议待扩展 |
| EQ、增益、均衡、重采样等 DSP | Audio Processor 内的处理节点 | 变换后的 PCM、延迟/尾音/时间映射 | 节点顺序、参数修订、能力协商、是否允许旁路 | Go gain 已有；外部节点、动态参数和更广效果待扩展 |
| 音频探测、指纹算法、响度分析 | 拟增分析扩展点；音频预处理复用 Audio Processor | 算法/版本、覆盖区间、测量值或指纹文件引用 | 稳定输入、算法配置、证据登记、有效性及任务配额 | 探测/指纹业务已有；可替换算法的插件契约未实现 |
| 匹配候选与对齐算法 | 拟增分析扩展点，和指纹提取分开能力 | 候选分数、依据、映射及验证范围 | Recording 关联、人工排除、自动阈值、TimelineEvidence 生效 | 现有核心算法不是外部插件；需专门结果与版本契约 |
| 标签解析与标签序列化 | Provider 适配内可替换库；通用外部版本为待建扩展点 | 标签结构或受控临时副本及差异 | 写回许可、字段选择、并发检测、备份/安全替换、新资产发布 | 受限写回已有；不得因插件化扩大现有 NTFS FLAC 范围 |
| 封面缩放、歌词格式转换 | 拟增内容变换扩展点；避免混入负责发现的 Scraper | 派生内容、源摘要、格式、变换版本 | 内容大小/格式校验、不可变发布、引用和回收 | 派生媒体业务已有；外部转换协议未实现 |
| 推荐排序、智能歌单规则 | 拟增有界策略扩展点；平台推荐仍属 Provider | 当前用户已授权候选的有序列表及依据 | 过滤权限、稳定条目/出处、快照事务、人工隐藏、循环检测 | 核心歌单/聚合已有；可安装策略尚未实现 |
| 播放记录导出、通知、外部同步 | 拟增事件消费扩展点 | 确认、重试建议、外部操作结果 | 最小字段授权、事件序列、投递游标、撤销、重试预算 | 未实现；写外部服务需独立权限，不能借 Provider 账号授权 |

后四类拟增扩展点先在核心定义小型适配接口，选择真实需求后再冻结外部角色/方法；表中中文职责不是已注册角色名。单个实现可以复用库，但插件 ID、角色实例、配置、账号及运行状态不能隐式合并。

对外部依赖的边界优先级高于“每个函数都做插件”：更换平台 API、编解码库、DSP 或指纹算法应只替换适配实现；鉴权、事务、修订和安全发布需要保持一个可信决策入口。没有外部替换需求的纯内部辅助函数保留普通模块。

## 3. 核心不能外包的职责

| 核心职责 | 可以委托的工作 | 必须由 Server 再校验和提交 |
| --- | --- | --- |
| 用户、账号和权限 | 平台授权交互与状态探测 | 本人/实例/账号归属、权限收回、密钥发放范围；不向 Client 或其他角色转交 Server 凭据 |
| 来源与资产 | 枚举、探测、版本证据 | externalId 映射、SourceAsset 创建、扫描完整性、缺失复核；插件不能自行标记 SHA-512 verified |
| Library 与匹配 | 指纹、候选分数、时间对齐建议 | 人工禁止关联优先、关联修订、证据版本、可逆审计；候选不得直接合并录音 |
| 歌单与推荐 | 上游分页、排序建议、规则求值 | 完整快照、出处/隐藏规则、任务代次、幂等与事务；失败不能发布成功空列表 |
| 播放与音频图 | 来源解析和媒体变换 | Resolver 最终选择、有效依赖租约、attempt 固定、Range/时间定位、恢复预算、两端不重复 DSP |
| 内容与原件 | 下载、解析、序列化、变换 | 类型/尺寸/摘要、人工锁、发布阶段、并发版本、原文件安全替换；插件不能自行覆盖音乐原件 |
| 持久化与恢复 | 实例私有键值、算法中间产物 | 核心表、数据库迁移、WAL/单写入队列、文件引用事务、备份清单与崩溃恢复 |
| 任务和生命周期 | 可取消任务执行、进度报告 | 配额、超时、排队、取消终态、准入与排空、晚结果拒绝、进程和临时资源回收 |

`host.state.*`、`host.database.*` 只提供实例隔离的受限状态，不是任意 SQL 接口，也不取代核心业务事务。插件结果先经大小、类型、归属、输入版本、运行代次和目标修订校验，再进入正常核心发布流程；校验失败不得以“可信官方插件”为由跳过。

## 4. 协议与 Host 扩展规则

### 4.1 沿用当前可用基线

- 控制面保持 stdio 的 `Content-Length` 帧、UTF-8 JSON、1 MiB 上限、200 项页上限和 `h-` / `w-` 请求 ID；stdout 仅协议，英文诊断写 stderr。
- 角色专用 `host.hello` 校验实例、nonce、配置修订及精确协议/插件要求；握手就绪前不接业务。`worker.ready` 是成功响应的逻辑含义，不是通用独立通知方法。
- `$/cancelRequest` 为统一取消通知；超时/取消后结果不可发布。音频控制方法和实际 DTO 以 [v1 Schema](contracts/plugins/v1/protocol.schema.json)为准，不能照长期设计自行发送 `audio.cancel`、任意图节点或共享内存字段。
- 音频、NCM 与 Scraper 分别复用已经验证的任务通道，校验任务/实例/资产版本、范围、取消和有效期；大块内容不进入控制 JSON。
- 网络能力声明不等于网络授权；本地文件根、公网目标、NAS 内网目标和外部事件接收方分别授权。

### 4.2 先补注册，再扩大功能

统一 Manager 已提供管理状态，但不是通用第三方加载器。新增 Worker 需登记固定插件身份、角色适配工厂、允许的配置声明、依赖和许可、握手验证、方法分发、数据通道及租约接入。注册成功后只发布实际通过的能力；未知能力不能自动获得权限或执行入口。

同包多角色可共享发布版本，但每个运行实例使用独立上下文。音频/NCM/Scraper 现有任务进程和 Provider 常驻进程遵守各自生命周期，不能为了“统一插件”强行假设所有 Worker 常驻或共享一个会话。

### 4.3 严格 Schema 的演进

当前协议包含严格对象、固定角色、固定方法和角色专用模型；`protocolVersion=1.0` 不等于允许增加任意字段。新的 analysis/content-transform/policy 等角色名尚未冻结，不写入现行配置或把草案字段塞入 `configuration` 绕过校验。

每个扩展按以下顺序推进：

1. 列出当前生产消费者、最小输入/结果、资源授权、预算、错误、取消与副作用；先确定能否复用既有角色。
2. 在 Server 维护的 Schema/协议说明与夹具中冻结新修订，明确旧 Host/Worker 拒绝或保留旧路径的行为；不偷偷更改已有字段含义。
3. 同步 Host 校验/注册、Worker 编解码、配置声明与迁移；跨端可见能力、来源类型、错误或状态有变化时评估 OpenAPI、事件和 Client/Web 兼容性。
4. 用真实新旧 Worker 组合验证接受/拒绝，再发布匹配制品。程序版本、协议版本、配置修订、算法版本和资产版本分别记录，不能相互代替。

仅新增内部算法实现且对外 DTO/行为完全不变时，保持公共 API；影响输出则更新算法/插件版本、缓存键和证据有效性，不能复用旧结果。新插件不得冒用内置 ID 来绕过 Host 白名单。

## 5. CMake / C++23 Worker 的开发约束

通用目录、工具链、目标编译属性、C ABI 和制品规则统一见[原生插件开发](../../docs/native-plugins.md)。Server 补充以下要求：

| 边界 | Server 约束 |
| --- | --- |
| 产物 | 独立可执行 Worker，遵循目标角色的现有 IPC；Go Host 不因 C++ 插件改为加载 DLL、cgo 或跨语言对象 |
| SDK | 先提供最小帧读写、DTO 校验、请求/取消、受控二进制读取帮助库；尚未交付，不要求生成器一次覆盖所有角色 |
| 原生依赖 | 固定版本/摘要与许可，构建信息记录实际编译器、目标系统/架构、C++23 特性支持和依赖；选择经过验证的必要特性 |
| Worker 内部动态库 | 确有可替换原生节点需求时使用版本化 C ABI、固定宽度字段、不透明句柄与明确所有权；C++ 类、STL、异常、分配器不跨边界 |
| 复用 Client 算法 | 共享算法源码与测试数据；Client DLL 导出层与 Server Worker 协议层独立，分别构建、测试和打包 |
| 包和启动 | CMake 安装到暂存目录，经制品清单显式加入安装包；不能假定当前 Go 构建或 `musicfs-plugins --plugin` 会自动发现原生 Worker |
| 日志与资源 | stdout 严格协议；stderr 英文日志脱敏且有界；每个请求有截止时间，子进程、线程、文件和通道在取消/退出时可回收 |
| 接入完成 | schema/契约夹具、真实 Go Host ↔ C++ Worker、错误与取消、数据校验、双平台打包/生命周期证据齐全后才声明支持 |

首个 C++ 验证优先选有明确原生依赖收益、无核心写入副作用的音频/分析算法。不得仅为统一语言迁移现有 Go Local Files、平台资料或 NCM 插件。若只需调用已验证外部命令，保留现有适配方式，是否增加 C++ 层由实际收益决定。

## 6. 配置、安装和生命周期

已实现的保存配置、运行状态、`operationId`、`restartRequired` 和配置应用语义继续以[插件管理](implementation/plugin-management.md)为准。以下安装/升级流程是补充设计，不代表管理 API 已提供下载或安装：

1. 管理员选择可信制品，检查平台、架构、协议、依赖、文件清单/摘要和许可；在新版本目录展开，禁用状态登记。
2. 校验配置声明、实例权限和凭据引用；只传本实例需要的运行配置，不能把所有 Server 环境变量和密钥传给 Worker。
3. 进行有界启动与握手探测，确认能力后才允许新工作。缺工具或配置仅令相关实例不可用，不阻塞无依赖来源。
4. 更新配置先保存期望修订，关闭新准入并排空旧工作；重建及资源检查成功后标记已应用。旧结果核对代次，不得覆盖新配置。
5. 升级先保存停用并正常停止 Server，确认资源释放后在新版本目录启动新 Worker；禁止覆盖运行文件。保留旧制品和配置/实例状态快照，状态迁移不兼容时停止升级并报告恢复步骤。
6. 失败回滚也须重新握手、校验配置及状态版本；不能让旧 Worker 读取新格式后继续写坏数据。核心数据库迁移仍由 Server 发布流程负责。
7. 卸载必须先保存停用并停止 Server，释放真实资源且确认无活动依赖；默认保留来源、人工内容、私有实例状态与凭据引用，数据删除/账号撤销为独立显式操作。

故障只隔离到依赖该插件的任务/会话，不发布部分成功产物；必要 DSP 失败明确中止，可旁路效果必须预先声明并经用户配置。第三方开放前追加 OS 文件/网络限制、资源上限和失控进程验证，不能以 IPC 或 manifest 替代。

## 7. 增量顺序与验收门槛

| 编号 | 工作及依赖 | 完成门槛 |
| --- | --- | --- |
| SP-01 | 固定身份接入清单与角色适配注册，复用 Manager | 新测试插件使用独立 ID；配置、授权、声明/实际能力、禁用、错误身份及旧插件回归通过 |
| SP-02 | 最小 CMake / C++23 Worker 及 SDK 试点，依赖 SP-01 | 真实 Go Host 双向 RPC、严格 DTO、取消、异常退出、二进制内容及构建安装通过；记录真实工具链 |
| SP-03 | 远端资源，沿用 NP-01/NP-02 | NAS/在线读取、版本变化、Range、摘要、Scraper/NCM/音频消费回归；具体依赖按[NAS计划](implementation/nas-bilibili.md) |
| SP-04 | 通用音频节点与分析结果契约，依赖 SP-01、相应算法验证 | 多节点协商、PCM/延迟/时间轴、指纹范围/版本、资源上限；结果只能由核心发布 |
| SP-05 | 内容变换、标签适配与策略扩展，按真实需求逐项推进 | 输入权限、确定性/版本、人工锁、快照/写回事务和失败保留验证；未选扩展不建空框架 |
| SP-06 | 安装/升级/回滚与可选第三方 SDK | 制品清单、干净环境启动、停服升级、状态兼容和恢复；不可信插件支持另以 OS 隔离验收为前提 |
