## 可重复资源负载

`tests/integration/resources` 是显式启用的 Windows 集成测量，平时测试仅跳过本项。它独立构建 Server、Local Files Worker 和音频 Worker，启动正式 CLI、YAML、鉴权及 SQLite，使用 client-managed 租约正常退出；不调用生产音乐目录和公网。

- 32 个 CC0 数学合成 WAV，每个 180 秒、48 kHz、PCM16 单声道，17,280,044 字节。
- 同一服务四轮固定负载；每轮 8 个新的完整 SHA-512 任务、8 个新的 120 秒指纹任务。
- hash 并发 1、总预算 4 MiB/s；fingerprint 并发 1；两个后台执行通道独立于播放。
- 每轮同时启动 2 路 WAV 原流和 2 路 MP3 处理流（-6 dB）。客户端接收缓冲设为 16 KiB，每 100 毫秒至多消费 8 KiB，形成真实慢消费者。
- 四路响应开始后等待 3 秒，取消未完成后台任务并停止播放，观察 8 秒。四轮后完整读取一次处理输出，再次读取同一资源并比较摘要；最后额外空闲 35 秒。
- 每轮验证所有自己生成的源文件均可用 `share=0` 独占只读打开，进程树只剩 Server 与常驻 Local Files Worker，缓存不超 128 MiB，取消后的 `.part` 不残留。已完成输出允许在有界缓存中保留。

采样间隔目标为 200 毫秒，实际间隔随系统枚举开销变化；原始 JSON 保存每次真实时间。Windows API 读取工作集、私有提交量、CPU 用户态加内核态时间、句柄数、线程数和本进程拥有的 IPv4 TCP 行，再递归统计整个 cacheRoot 与 mediaRoot。只包含被测服务及其子进程，排除测试程序、编译器和其他应用。进程可能在两次采样间启动并退出，因此峰值与短命子进程 CPU 是观察值或下界，不是连续测量的严格最大值；工作集与私有提交量含义不同，不可相加。

当前原始记录位于忽略目录 `build/_resource-validation`，包含实际二进制 SHA-256、工具摘要、任务结果、各阶段采样和缓存变化；不记录令牌、音乐路径和私人曲名。

## 初轮观测与进一步检查

完整输出缓存接入前，较早的两轮探索测量观测 69.92 秒，测试总耗时 96.99 秒。服务树峰值 11 个进程、工作集 191,918,080 字节、私有提交量 446,148,608 字节、2,330 个句柄；播放输入缓存峰值 69,120,176 字节，停止后归零。指纹文件是持久媒体，结束时 mediaRoot 的 139,437 字节应保留，不计作缓存泄漏。

主进程句柄从 273 增至 334、356，额外空闲 35 秒仍为 356；工作集从 32,202,752 字节到最终 35,991,552 字节。此时不能把句柄残留归因为线程或宣称不存在泄漏，因此追加四轮固定负载、线程/TCP 计数和独占源文件检查。

四轮之后观察到收敛，未出现每轮固定增量；线程和暂留连接也有变化，但没有逐个句柄分类，所以不将全部残留句柄断言为 Go 线程。每轮 32 个合成源均可独占重开；所有收尾采样只剩两个预期常驻进程，未留 FFmpeg、fpcalc 或音频 Worker。此结果不能代替长时间运行泄漏测试。

缓存峰值为 69,120,176 字节，是四个输入快照；后台任务未阻止四路播放输出实际字节。每轮 hash 成功 1 个、取消 7 个，fingerprint 成功 8 个；本轮合计 4 个完整摘要和 32 份指纹，mediaRoot 最终为 371,823 字节。16 次后台取消请求一组用时依次为 35.002、32.573、40.714、44.123 毫秒，这是请求耗时，不等同于所有资源当时已经清理；后者由随后的 8 秒检查确认。

原树枚举记录曾报告 11 个进程、工作集 237,019,136 字节、私有提交量 481,038,336 字节、2,909 个句柄。随后逐进程审计发现其中一次包含非本负载的 `vctip.exe`：Windows 仅保存数值父 PID，旧孤儿进程可能碰到被复用的父 PID。因此这组树峰值被标为污染观测，不作为正式资源上限；上表直接按实际 Server PID 读取的句柄/线程/内存和独占源文件检查不受影响。采样器已增加父子创建时刻核对及回归用例，正式缓存复测将使用修正后的树，不按进程名静默丢弃未知项。

从负载前最后采样到最终采样，主进程消耗 CPU 8.765625 秒 / 墙钟 88.7961664 秒，约占一个逻辑处理器的 9.87%；这不包含 Worker。子进程只能累加被采到的 CPU 时间下界，不能据此推出真实完整树平均 CPU 或吞吐。

本轮构建的 Server SHA-256 为 `1615a498c72e2284e0f088001acebf62e91db98f7e27d9e337ab49bf2ecf9e2d`，Local Files Worker 为 `93dd0ed31f65c87b7c0df03594d544a5a6c3348deac4da58d1962d144d119698`，音频 Worker 为 `83ccd8e9aa7888489076586a86c20b3309fc4070440091d746e478f216b651b8`。摘要用于区分本轮实际执行文件，不是已发布制品标识。原始记录为 `windows-four-cycles-before-output-cache.json`。

## 执行入口

在仓库根设置已验证工具的绝对路径；报告位置放入忽略的 build 目录。以下占位值须替换为本机安装位置：

```powershell
$env:MUSICFS_RESOURCE_BASELINE = '1'
$env:MUSICFS_FFMPEG = '/absolute/path/to/ffmpeg.exe'
$env:MUSICFS_FFPROBE = '/absolute/path/to/ffprobe.exe'
$env:MUSICFS_FPCALC = '/absolute/path/to/fpcalc.exe'
$env:MUSICFS_RESOURCE_REPORT = 'build/_resource-validation/windows.json'
go test -mod=readonly -buildvcs=false -count=1 -v ./tests/integration/resources -run TestResourceBaselineActualServer
```

测量中的被测可执行程序采用普通构建；不把 race 插桩程序的资源占用当部署数字。默认并发/缓存设置是该轮输入约束，不能仅凭本机成功推出更高默认值；达到上限时的排队/拒绝、任务取消与恢复仍由各领域的边界测试负责。
